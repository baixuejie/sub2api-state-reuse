# 升级、回退与运维

## 上线前

- 在隔离号池验证版本、插件能力、表结构与目录映射。
- 备份当前插件包、配置、**非空账号路由范围**、采集器脚本、systemd/nginx配置。
- 确认专用Clash核心和SSH持续在线，IP管理代理启用且未过期。
- 用自有账号跑完整采集和携票复验，再核对 `renewed`、实际票据长度、分组与真实流式响应。
- 确认普通用户看不到日志；HTTP 200头不等于上游流完整结束。

## 升级

1. 在工作副本修改代码、运行 `make check test build`，保留同一个 `publisher.key`。
2. 暂停 `state-collector.timer`，等待正在运行的 `state-collector.service` 结束。不要并行写多套采集状态。
3. 在号池后台备份插件配置和路由，升级包。宿主若要求停用再上传，会有插件短暂不可用窗口，选择合适的维护时间。
4. 检查新版本、runtime healthy、账号范围和rollout；不要因上传后绑定重置而启用空范围。
5. 同步采集器/monitor源码，重启 `state-monitor.service`，手动启动一轮collector验证，再恢复timer。
6. 观察采集事件、插件audit和账号实际响应，不只看UI颜色。

仅修改HTML/JS时可以同步静态文件后刷新，无需重启主站；修改server.py需要重启monitor。变更nginx先`nginx -t`。

## 回退

停止定时器并等待当前轮结束，恢复上一版插件包、配置、路由和采集器脚本，再确认健康并启用timer。恢复nginx后测试再reload。

保留数据库、票据和业务数据，不从旧数据库备份覆盖当前写入。若旧版不支持292，必须同步回退Python分组策略，不能让Python判为有效但插件拒绝导入。

## 已知边界

- 本地机器离线，Clash通道随之不可用；不会自动唤醒电脑。
- 票据形态和上游模型字段可能变化；292/332是本项目的经验条件，不能保证能力永远不变。
- 默认采集范围仅两个配置分组，账号状态和可调度约束都生效。
- 插件请求内续采与外部采集器是两条路径：前者没有Python二次复验，也不共享其持久冷却；插件也可能产生额外请求。需要统一调度时，应先新增明确的插件禁用内采开关并补齐测试。
- 每20秒触发检查，缺票账号一轮一个出口；有效票续采仍间隔300秒。上一轮未结束时不会重叠，因此长请求/大批量时实际间隔会长于20秒。每轮150秒采集预算、进程上限270秒。
- 迁移到20秒调度必须停用旧cron或旧timer；保留现有429恢复时间和认证暂停。轮换路由不等于保证真实出口IP不同。
- 候选先原子交给插件，再通过生产账号测试触发消费。该测试使用账号业务代理，可能失败；页面区分候选与已入库。
- Python monitor使用标准库HTTP服务、监听loopback，通过nginx提供外部TLS；不要直接暴露其端口。
- 旧日志行被截断或损坏会跳过，显示最近500条；历史完整性以你的日志保存策略为准。
